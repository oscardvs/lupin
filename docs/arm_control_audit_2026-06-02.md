# Lupin Arm-Control Page — Audit & Recommendation (final)

## 1. Verdict

The direct per-joint angle command path is **not the root problem** — it is sound, and it drives the *same two controllers MoveIt would drive* (`mirte_master_arm_controller` + `mirte_master_gripper_controller`). The "unreliable and not robust" feeling comes from a cluster of **layer bugs sitting on top of a correct command path**:

1. **The enable/disable hiccup (#1).** The Enable/Disable button toggles bus-wide servo *torque* (`/io/servo/hiwonder/enable_all_servos`), which is completely decoupled from the HW interface's own command gate (`enable_arm_control`). So a "disabled" arm sags, the controller re-asserts a stale setpoint when re-energized, and the arm lurches.
2. **Symmetric ±90° joint windows that don't match the real asymmetric servo limits (#3).** Two joints (pan, lift) can be commanded past the servo's silent-reject point at the negative end; two others (elbow, wrist) are needlessly capped ~25° short.
3. **Every "ack" means "trajectory dispatched," not "joint arrived" (#6).** Failed, stalled, or silently-rejected moves look successful.
4. **No arbitration on the shared trajectory topic (#7).** On hardware, three nodes publish to one un-arbitrated `joint_trajectory` topic with independently-seeded private command caches.

**MoveIt fixes none of these.** Every stated complaint lives in the HMI/bridge/HW-interface layer, all orthogonal to motion planning. MoveIt would add a planning layer the arm's two real jobs (camera-tilt onto an AprilTag; top-down tulip pick) don't need, on a 4-DOF arm where the vendor's KDL config can't reliably solve full 6-DOF pose goals.

> **Correction integrated (technical-correctness lens, high confidence):** an earlier draft argued MoveIt would worsen contention by becoming a "fifth publisher on the un-mux'd trajectory topic." That is **wrong**. MoveIt drives the JTC via the **FollowJointTrajectory action** (`moveit_controllers.yaml: action_ns: follow_joint_trajectory`), not by publishing to the `joint_trajectory` *topic*. The JTC internally serializes action goals (a new goal preempts the running one), so MoveIt would route *around* the un-arbitrated topic and use a *more* robust interface than the bridge does today — exactly the interface finding #6 recommends. The contention argument against MoveIt is therefore retracted. The decision is unchanged because the real reasons to defer (4-DOF KDL, config defects, no Servo installed, non-turnkey browser integration) stand on their own.

**Recommendation: Option A — harden the existing direct-control path.** Within Option A, do a **tight demo-critical subset first** (see §5), then the remaining correctness/maintainability debt as time allows. Reserve a *sim-only* MoveIt spike strictly for *if* tulip-picking later acquires hard collision-avoidance or planned multi-waypoint requirements — with the honest caveat that even that spike's payoff is capped by the 4-DOF KDL limitation.

Confidence: **high** on the diagnosis (all load-bearing facts independently verified by three lenses against source). The *fixes* for complaint 1 (enable/disable) and the gripper direction/limits are **plausible but not yet proven on hardware** — see "must be verified live" in §5.

## 2. How it works today

```
HMI ArmView slider (onValueCommit, per-joint, on release)
   │  callService(SetServoAngleWithSpeed {angle, rate, degrees:true})
   │    arm joints → /lupin/arm/<id>/set_angle_with_speed
   │    gripper    → /lupin/gripper/set_angle_with_speed
   ▼
gripper_action_bridge.py  (serves those services)
   │  • clamps arm to ±π/2 ; maps gripper ±30° → [-0.20,+0.25] rad
   │  • merges the ONE commanded joint with the other 3 from last /joint_states
   │  • returns status:True the instant it PUBLISHES (dispatch ack, NOT done)
   ▼
/mirte_master_arm_controller/joint_trajectory   (4-joint JointTrajectory; gripper → /…/gripper_cmd GripperCommand action)
   │  ⚠ on hardware also published by arm_preset_server + arm_teleop — THREE live publishers, NO mux/arbiter
   │    (arm_sim_shim is a 4th publisher in SIM ONLY)
   ▼
JointTrajectoryController (allow_partial_joints_goal:false, open_loop_control:true) @ 10 Hz
   │   ↳ uses each point's velocity to SHAPE the interpolated per-tick position setpoints
   ▼
MirteMasterArmHWInterface.write()  (re-asserts hw_commands_ when |Δ|>0.05 rad OR servo.moved)
   │  forwards POSITION ONLY via /io/servo/hiwonder/<servo>/set_angle (mirte_msgs/SetServoAngle, degrees=false)
   │  ⚠ fire-and-forget (async_send_request, response never read) — velocity never reaches HW
   ▼
Hiwonder servo  → REJECTS out-of-range angle with status=false (silently dropped, response unread)

Feedback: read() copies REAL servo position from /io/servo/hiwonder/<servo>/position into /joint_states (genuine, not command-echo; velocity NaN).
Enable/Disable button: SEPARATE path → /io/servo/hiwonder/enable_all_servos (bus torque toggle, all 5 servos).
   ⚠ The HW interface has its OWN gate (service enable_arm_control) that the HMI never touches.
     on_activate() copies hw_commands_ = hw_states_ from live feedback (this is the natural re-pin point).
```

Three things to internalize:

- **Torque and command are two independent switches the HMI conflates.** `enable_all_servos{false}` cuts *torque* (arm goes limp) but the HW interface's command gate stays open and keeps firing `set_angle`. `enable_arm_control{false}` stops the HW interface re-asserting but does **not** cut torque. Today the HMI only ever touches the first one.
- **"Ack" is a dispatch receipt, never a completion signal** — the path is open-loop on a plain topic with fire-and-forget servo calls.
- **`on_activate()` already re-pins `hw_commands_` from live state** (copies `hw_states_`). That existing behavior is the cleanest lever for the lurch fix (§5).

**Verified joint-limit ground truth** (corroborated by 3 independent investigators; load-bearing for #3/#4/#10):

| Joint | URDF (arm.xacro) / HMI today | **REAL servo software limit** | Mismatch |
|-------|------------------------------|-------------------------------|----------|
| shoulder_pan | ±90° (±π/2) | **−86.0° … +90.0°** | HMI over-travels to −90° → servo can reject at neg. stop |
| shoulder_lift | ±90° | **−86.2° … +85.5°** | HMI over-travels both ends → reject |
| elbow | ±90° | **−116.3° … +92.5°** | HMI under-travels ~26° (lost reach) |
| wrist | ±90° | **−110.7° … +88.0°** | HMI under-travels ~21° (lost reach) |
| gripper_joint | ±30° HMI → [−0.20,+0.25] rad | **−43.6° … +37.0°** (≈[−0.76,+0.65] rad) | window unverified; uses small slice |

> **Reproduction formula — corrected.** An earlier draft wrote the recipe as `min_angle_in = deg((min_angle_out − home_out)/100)`, which is wrong twice over: the quotient `(angle_out − home_out)/100` is **already the limit in degrees**, and the servo then *stores* it as radians via `deg_to_rad`. A maintainer literally applying a rad→deg `deg(...)` to that quotient gets garbage (e.g. ~−4927°). The correct parser logic (`hiwonder_servo_data.cpp:120-126`) is: `deg = (angle_out − home_out)/100`, then `rad = deg_to_rad(deg)`. The **table values above are all correct** (reproduced to the tenth of a degree from `mirte_master_config.yaml:104-133`); only the prior formula notation was wrong.

> **Where the over-travel actually rejects — corrected.** The HMI value does **not** reach the servo unfiltered. A slider command first passes the bridge's clamp to ±π/2 (`gripper_action_bridge.py:93`) and then the JTC's own URDF position limits, before the HW interface forwards it to the servo via `set_angle` (fire-and-forget, `degrees=false`, response never read at `cpp:73-74`). Consequences: for **elbow/wrist** the HMI ±90° is *clamped by the bridge* and never even reaches the servo's wider limit — they are under-travelled, not rejected. Only **pan/lift** (servo limit < 90° at the negative end, inside the URDF ±90°) can actually hit the servo's silent reject. So the user-visible "send failed near the negative stop" is a pan/lift phenomenon; the elbow/wrist issue is purely lost reach.

## 4. The MoveIt question

**Does the vendor support MoveIt on hardware?** Yes — genuinely, not just sim. The vendor tutorial states "MoveIt2 is already installed on the MIRTE Master" and launches with `use_sim_time:=False`. The apparent red flag (the moveit_config `ros2_control` xacro uses `mock_components/GenericSystem`) is **not** instantiated by `move_group`: `mirte_moveit.launch.py` starts **only** `move_group` + RViz, no controller spawner.

> **Precision (technical-correctness lens):** `move_group` does **not** "attach to" or instantiate any hardware controller. It talks to `controller_manager` over the action interfaces in `moveit_controllers.yaml`. Whether those resolve to real or mock hardware depends entirely on **which URDF the team's bring-up feeds `controller_manager`** — not on anything inside `mirte_moveit_config`. The conclusion (the mock plugin is irrelevant to the hardware path) is correct; the *reason* is this bring-up-URDF dependency, which must be verified rather than assumed. The team's real HW interface exports genuine position feedback, so MoveIt execution monitoring would be trustworthy **if** the bring-up URDF is the real one.

**Does `mirte_moveit_config` work as-is?** No — it's an unreviewed Setup-Assistant dump with real defects:
- **SRDF `home` = (0,0,0,0)** (`:23-28`) contradicts the team's measured safe pose `(0.04,−0.01,0.01,−1.57)`, which minimizes the gravity moment on the thermally-fragile `shoulder_lift` servo. MoveIt "home" would drive to a *different, less-safe* pose than every existing Home path.
- **`joint_limits.yaml` has velocity but NO position or acceleration limits** (`has_acceleration_limits:false` everywhere). Position falls back to the URDF (inheriting the too-narrow ±90° elbow/wrist envelope); jerk-unbounded TOTG on a 10 Hz open-loop controller risks overshoot on the fragile servo.
- **KDL solver, NO `position_only_ik`, on a 4-DOF arm** — full 6-DOF pose goals (MoveIt's flagship feature) will mostly fail IK; the vendor itself flags "the blue selector in RViz is not usable." Only joint-space/named-pose goals are reliable.
- SRDF gripper group defined by a *link* (`:20`); `frame_base_joint` (fixed) listed in the arm group (`:17`); duplicate YAML keys. Cosmetic, but they confirm the config is untrusted on hardware.

**Does MoveIt solve the user's complaint?** **No.** Every actual complaint lives in the HMI/bridge/HW-interface layer: the enable/disable hiccup is the wrong-service bug (#1), the joint limits are URDF/calibration data (#3/#4), single-joint reliability is the ack/feedback gap (#6) — all orthogonal to MoveIt. MoveIt drives the *same two controllers* the bridge already drives.

> **Retracted argument (technical-correctness lens):** earlier drafts claimed MoveIt "adds a planning layer on the same un-arbitrated, open-loop, 10 Hz contention surface — a fifth fighting publisher (#7)." This is **wrong** and is withdrawn. MoveIt sends **FollowJointTrajectory action goals** (`moveit_controllers.yaml: action_ns: follow_joint_trajectory`), which the JTC **internally serializes** (a new goal preempts the active one). MoveIt does **not** add a publisher to the un-mux'd `joint_trajectory` topic, and would in fact use the *more robust* action interface (the one finding #6 wants). The case to defer MoveIt does **not** rest on contention — it rests on the four points below.

**Is it overkill for this arm's jobs?** Yes, and this is the real argument:
- Job (a) camera-tilt/AprilTag = a single wrist named pose. Job (b) top-down tulip pick = one approach pose reachable with a tiny analytic or position-only IK. Neither needs collision-aware multi-waypoint Cartesian planning — the only thing MoveIt adds — and the 4-DOF KDL config can't reliably deliver 6-DOF goals anyway.
- **Browser integration is real and non-turnkey:** no MoveIt Servo installed; the MoveGroup action over rosbridge needs a rosbridge new enough for `send_action_goal` plus hand-built nested `MotionPlanRequest` JSON; precedent (ur5_webgui) needed author help. A headless `move_group` must be added to bring-up.
- **Config remediation is most of a week** (SRDF home, position+accel limits, swap the mock plugin for `MirteMasterArmHWInterface` in the bring-up URDF path).

**Decision: Option A — harden the direct-control path. Do NOT adopt MoveIt for v1.** Treat MoveIt as a **post-course / next-iteration investment**, not a spike to slot in mid-timeline. Even a sim-only spike's payoff is capped: with 4-DOF KDL and no `position_only_ik` (the vendor's own "blue selector not usable" admission), the headline collision-aware-6-DOF-planning benefit is largely unavailable. Trigger the spike **only if** tulip-picking later acquires a hard collision-avoidance or planned-multi-waypoint requirement — and budget it honestly.

## 5. Recommended plan (Option A)

Ranked by **demo impact**, not engineering severity. Split into desk-time (LoC, no robot) and robot-bench time (each failed iteration on Mirte-247264 costs a power-cycle + 60–90 s cold-boot load storm + clock-sync; the shoulder_lift thermal latch needs a power-cycle to clear). Schedule robot-bench time explicitly against demo day.

### Tier 0 — demo-critical subset (the tight core that changes what the client sees)

These three map directly to the three stated complaints. Almost all HMI/bridge TypeScript + Python; one live validation pass.

1. **Fix Enable/Disable (#1/#2/#12) — desk + 1 robot-bench validation.** On Disable, deactivate the JTC (so it stops re-asserting) and hit `enable_all_servos{false}` for torque; **on re-enable, reactivating the JTC re-pins `hw_commands_=hw_states_` via the existing `on_activate()`** — no new re-pin code needed.
